CATALYX BACKEND — SIMPLE SUMMARY
==================================
WHAT IS THIS PROJECT?
----------------------
Catalyx is a backend server (built with Java + Spring Boot) for an app where
a business owner can sign up, log in, and set up their business profile.
Later phases (not built yet) will let them add products and use AI to
generate a catalogue for their business.

Think of it like the "engine room" of the app — it has no visual screens,
just the logic and database that a mobile/web app would talk to over the
internet using API calls (like /signup, /login, /business).


PHASE 1 — PROJECT SETUP AND ENVIRONMENT
-----------------------------------------
This phase was about laying the foundation, before writing any real feature.

What we did:
- Created a new Spring Boot project called "catalyx-backend" using Java 17.
- Set up the project to talk to a PostgreSQL database (a place to store data
  permanently, like users, businesses, products).
- Added the basic building blocks (folders) for how the code will be
  organized: config, controller, dto, entity, repository, security, service.
  (Explained in detail in architecture.txt)
- Created the 6 main "entities" — these are the tables in our database:
  User, Business, Product, ProductImage, Catalogue, AiJob.
  These represent the real-world things our app manages.
- Created "repository" files for each entity — these are helper classes
  that let our code save/fetch/delete data from the database without
  writing raw SQL by hand.
- Wrote the application settings file (application.properties) that tells
  the app which database to connect to.

In short: Phase 1 = "build the skeleton and connect to the database."


PHASE 2 & 3 — AUTHENTICATION & JWT (Login System)
----------------------------------------------------
(This was committed as one combined phase called "Authentication & JWT")

This phase is about letting users create an account and log in safely.

What we did:
- Built a Signup API (/signup): a new user gives their name, email, and
  password, and we create their account. The password is never stored as
  plain text — it's scrambled using a one-way encryption method called
  BCrypt, so even we can't see the real password.
- Built a Login API (/login): user enters email + password, and if correct,
  we give them back a "token" — a digital pass (like a wristband at an
  event) that proves who they are.
- This digital pass is called a JWT (JSON Web Token). It's a small piece of
  text that:
    - Contains the user's identity (email, user ID)
    - Has an expiry (24 hours by default)
    - Is signed/sealed with a secret key so nobody can fake or edit it
- Every time the user calls another API (like creating a business), they
  attach this token in the request. Our server checks the token to confirm
  "yes, this is really this user" before allowing the action — this is
  called being "authenticated."
- If someone provides a wrong password, an invalid token, or no token at
  all when required, we return a clean, readable error message (not a
  scary server crash) — for example "Invalid email or password."
- We also added Spring Security — a security guard system that decides
  which pages/APIs are public (like /signup, /login) and which ones
  require you to be logged in (everything else).

In short: Phase 2/3 = "let people create accounts, log in safely, and
protect the rest of the app so only logged-in users can use it."


PHASE 4 — BUSINESS SETUP MODULE
-----------------------------------
Now that users can log in, this phase lets them set up their business.

What we did:
- Built a "Create Business" API (POST /business): a logged-in user can
  register their business by giving a name, category (e.g. "Bakery",
  "Clothing"), logo image link, and brand colors.
- Built a "Get Business" API (GET /business): a logged-in user can fetch
  their own business details.
- Rule: each user can only have ONE business. If they try to create a
  second one, the app blocks it with a clear error ("A business already
  exists for this user").
- The business is always linked to the exact user who is logged in — we
  use their token to know who they are, so nobody can create or see
  another person's business.

In short: Phase 4 = "let a logged-in user create and view their own
business profile."


PHASE 5 — PRODUCT MANAGEMENT (Add Products + Upload Photos)
---------------------------------------------------------------
Now that a user can log in and set up their business, this phase lets them
add products to that business, along with photos of each product.

What we did:
- Built a "Create Product" API (POST /products): a logged-in user can add
  a new product under their business by giving a name, SKU (product
  code), price, and description.
- Along with the product details, the user can also upload one or more
  photos of the product in the SAME request (this is called a
  "multipart" request — a mix of text fields and file uploads together).
- Built a "Get Products" API (GET /products): a logged-in user can fetch
  the full list of their business's products, each with its photos
  included.
- Added a new helper, FileStorageService, whose only job is handling
  uploaded photos safely:
    - Rejects empty files.
    - Only allows real image files (JPEG, PNG, GIF, WEBP) — blocks
      anything else (like a disguised .exe file) from being uploaded.
    - Rejects any single photo bigger than 5MB.
    - Saves each accepted photo to a folder on disk organized by product
      (uploads/products/<productId>/), with a random, unique file name
      so two different people's uploads never overwrite each other.
- Every uploaded photo becomes its own row in the ProductImage table
  (already designed back in Phase 1), linked to the product it belongs to.
- Added server-wide limits: no single uploaded file over 5MB, and no
  request (all files combined) over 25MB — if someone tries to break
  this, the app now replies with a clean error message ("Uploaded file(s)
  exceed the maximum allowed size") instead of crashing.
- A product can only be created under the business that belongs to the
  logged-in user — same ownership protection pattern as Phase 4's
  business rule.
- Small supporting change: added one query that fetches a business's
  products AND their photos together in a single efficient database
  call, instead of needing separate lookups.

In short: Phase 5 = "let a logged-in user add products to their business,
with photo uploads, safely validated and stored."


PHASE 6 — AI IMAGE VALIDATION (Photo Quality Check)
------------------------------------------------------
Before we ask an AI to build a nice catalogue from a product photo, we
first need to make sure the photo is actually good enough to use. A tiny
or blurry photo would produce an ugly result. Phase 6 adds an automatic
quality check that every uploaded photo now passes through.

Important: this check is NOT AI. It uses simple, fixed math rules, so the
same photo always gets the same result — predictable and repeatable.

What we did:
- Added a new helper file (app/validation.py) with one function,
  validate_image(), that inspects a photo and checks two things:
    1. Resolution (size): the photo must be at least 400 x 400 pixels.
       Anything smaller is flagged as too low quality.
    2. Sharpness (blur): using a well-known technique called "Laplacian
       variance" (from the OpenCV image library), we measure how much
       fine detail / edges the photo has. A sharp photo scores high; a
       blurry one scores low. If it scores below the threshold, it's
       flagged as blurry.
- The check gives back a simple verdict for each photo:
    - "READY_FOR_AI_GENERATION"  -> photo passed, good to use
    - "NEEDS_ATTENTION"          -> photo failed one or more checks
  ...plus a plain-English list of reasons for any failure, e.g.
  "Resolution 150x150 is below the minimum 400x400." or
  "Image appears blurry (sharpness score 0.7 is below the 100 threshold)."
- If a file is corrupt or unreadable, it's simply marked "NEEDS_ATTENTION"
  with a reason — it does not crash the upload, and other photos in the
  same upload are still processed normally.
- Two new columns were added to the ProductImage table:
  validation_status and validation_reasons, so each photo's verdict is
  saved in the database next to the photo.
- The "Create Product" API (POST /products) from Phase 5 now runs this
  check automatically on every uploaded photo and stores the result. The
  user doesn't do anything extra — it just happens.
- The "Get Products" API (GET /products) now includes each photo's
  validation status and reasons in its response, so the app can show the
  user which photos need to be replaced.
- Installed two standard image libraries to do this: Pillow (for reading
  image size) and opencv-python-headless (for the blur measurement).
- Photos uploaded before Phase 6 simply show an empty/blank status — they
  were never checked, and that's fine.

In short: Phase 6 = "automatically check every uploaded product photo for
size and blur, label it READY or NEEDS ATTENTION, and save that verdict."


PHASE 7 — GEMINI AI INTEGRATION & CATALOGUE GENERATION
--------------------------------------------------------
This is the first phase where the app actually uses AI.

THE SIMPLE IDEA:
The user already has products saved (with a name and a description they
typed in earlier phases). In Phase 7, the user picks one product and the
app asks Google's Gemini AI to write nice marketing text for it:
  - a catchy headline
  - a short 2-3 sentence description
  - 3-5 "key features" bullet points

Important: the AI only reads the product's NAME and DESCRIPTION (text).
It does NOT look at the product photo. The photo checks were Phase 6;
this is a separate step.

HOW IT WORKS (step by step):
1. The user (logged in) calls POST /generate and sends one product's ID.
2. The app checks that product really belongs to this user. If not, it
   replies "Product not found for this account."
3. The app creates an "AI Job" in the database and marks it "PROCESSING"
   (like a ticket that says "work in progress").
4. The app sends the product name + description to Gemini and waits for
   the reply.
5. The app updates the job:
     - "DONE"   -> the AI text is saved in the job
     - "FAILED" -> a short error message is saved instead (for example:
                   no API key, network problem, or empty reply)
6. Either way the app replies normally. An AI problem never crashes the
   request - it just becomes a "FAILED" job with a reason.
7. Later, the user can call GET /status/<job_id> to check the job and
   read the result. Users can only see their own jobs.

WHERE THE AI CODE LIVES:
- All the Gemini code is in ONE file: app/ai_service.py.
- The rest of the app just calls one function and doesn't know or care
  that it's Gemini.
- So if we ever switch to another AI (OpenAI, Claude, etc.), we only
  change that one file - nothing else.

SAFETY / SETUP:
- The Gemini API key is read from an environment variable (GEMINI_API_KEY).
  It is never written in the code and never printed in logs.
- If the key is missing, generation just fails cleanly (a "FAILED" job
  that says the key isn't set) - the app still runs fine.
- One new library was installed: google-generativeai (Google's official
  Gemini SDK for Python).

DATABASE:
- The AiJob table (designed back in Phase 1) is now used for real. Each
  attempt is one row: which product, the status
  (PROCESSING / DONE / FAILED), and the result text.

IN SHORT:
Phase 7 = "user picks a product -> Gemini AI writes catalogue text for it
-> saved as a job that ends DONE or FAILED -> all AI code kept in one
easy-to-swap file."
