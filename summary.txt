========================================
 PHASE 1 — PROJECT SETUP & ENVIRONMENT
========================================

WHAT IS PHASE 1?
----------------
Phase 1 is the starting point of the "catalyx-backend-py" project.
The goal of this phase is simple: get a working Python backend skeleton
running on the machine, with all the tools and libraries it will need
later already installed. Nothing about business logic, databases, or
authentication is built yet — this phase only proves that the project
runs and is ready for real development.

Think of it as laying the foundation and turning the lights on before
any rooms are built.


WHAT WAS ACTUALLY DONE
----------------------
1. A dedicated Python environment was created.
   - Tool: Python 3.14's built-in "venv"
   - Folder: .venv/
   - Why: keeps this project's libraries separate from the rest of the
     computer, so versions never clash with other projects.

2. All required libraries were installed into that environment:
   - fastapi          -> the web framework used to build the API
   - uvicorn          -> the server that runs the FastAPI app
   - sqlalchemy       -> talks to the database (used in a later phase)
   - psycopg2-binary  -> lets SQLAlchemy connect to PostgreSQL
   - python-jose      -> creates and verifies JWT tokens (auth, later)
   - passlib          -> password hashing helpers (auth, later)
   - bcrypt           -> the actual hashing algorithm passlib uses
   - python-multipart -> lets the API accept form data / file uploads
   The exact versions are frozen in requirements.txt so the setup can
   be reproduced later or by someone else.

3. The project folder structure was created:

   app-backend/
   |-- .venv/             (the virtual environment - not committed)
   |-- .gitignore         (tells git to ignore .venv, caches, .env)
   |-- requirements.txt   (the exact list of installed packages)
   |-- summary.txt        (this file)
   |-- app/
       |-- __init__.py    (marks "app" as a Python package)
       |-- main.py        (the application itself)

4. A minimal application was written in app/main.py.
   It creates a FastAPI app and exposes ONE route:

       GET  /   ->   {"status": "ok",
                      "message": "catalyx-backend-py is running"}

   This is called a "health-check" route. Its only job is to answer
   "yes, I'm alive" when something asks. It is the standard way to
   confirm a web service started correctly.


HOW WE KNOW IT WORKS
--------------------
The server was started with:

    .venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8080

and a request was sent to http://127.0.0.1:8080/ .

Result:
    HTTP 200 OK
    {"status":"ok","message":"catalyx-backend-py is running"}

The server logs showed a clean startup ("Application startup complete")
and it shut down without errors. Phase 1 is verified.


HOW TO RUN IT YOURSELF
----------------------
From the app-backend folder:

    source .venv/bin/activate
    uvicorn app.main:app --port 8080 --reload

Then open http://127.0.0.1:8080/ in a browser, or run:

    curl http://127.0.0.1:8080/

The interactive API docs are also available at:

    http://127.0.0.1:8080/docs

========================================
 PHASE 2 — DATABASE MODELS & CONNECTION
========================================

WHAT IS PHASE 2?
----------------
Phase 1 turned the lights on: a bare FastAPI app that could say
"I'm alive". Phase 2 gives that app a memory.

The goal of this phase is to connect the backend to a real
PostgreSQL database and describe, in Python, every table the
project will store data in. After this phase the app knows HOW
to talk to the database and WHAT its data looks like. It still
has no real endpoints — that comes next.

Think of it as installing the filing cabinets and labelling
every drawer before anyone starts filing papers.


WHAT WAS ACTUALLY DONE
----------------------
1. A database connection was set up (app/database.py).
   - engine        -> the actual pipe to PostgreSQL
   - SessionLocal  -> hands out short-lived "conversations" with the DB
   - Base          -> the parent class every table model inherits from
   - get_db()      -> a helper FastAPI will use to give each request
                      its own database session and clean it up after
   The database it connects to is called "catalyx_db". The address
   can be changed with a DATABASE_URL environment variable.

2. Six tables were described as Python classes (app/models.py):

   - User          people who log in
                   (id, email [unique], password, name, created_at)

   - Business       a company owned by a user
                   (id, user_id, name, category, logo_url,
                    brand_colors, created_at)

   - Product        an item that belongs to a business
                   (id, business_id, name, sku, price,
                    description, created_at)

   - ProductImage   a photo that belongs to a product
                   (id, product_id, image_url, uploaded_at)

   - AiJob          a background AI task for a product
                   (id, product_id, status [default "PENDING"],
                    result, created_at, updated_at)

   - Catalogue      the finished output of an AiJob for a business
                   (id, ai_job_id, business_id, template_name,
                    content_url, created_at)

   The tables are linked with foreign keys (e.g. a Product points
   to its Business, a ProductImage points to its Product). Product
   and ProductImage also have a two-way relationship: from a
   product you can read product.images, and deleting a product
   deletes its images automatically.

3. Automatic table creation was wired up (app/main.py).
   On startup the app now runs Base.metadata.create_all(), which
   creates any of the six tables that don't already exist in
   catalyx_db. No manual SQL needed.


HOW WE KNOW IT WORKS
--------------------
The app was started and it:
   - connected to catalyx_db with no errors
   - created all six tables (users, businesses, products,
     product_images, ai_jobs, catalogues)
   - set up the foreign keys correctly
   - logged "Application startup complete"
   - still answered GET / with HTTP 200 and
     {"status":"ok","message":"catalyx-backend-py is running"}


FILES ADDED / CHANGED
---------------------
   app/database.py   (new)  connection, session, get_db()
   app/models.py     (new)  the six table models
   app/main.py       (edit) runs create_all() on startup

========================================
 PHASE 3 — AUTHENTICATION & JWT
========================================

WHAT IS PHASE 3?
----------------


The goal of this phase is to let real people create an account
and sign in. When someone signs up or logs in, the backend hands
them a "token" — a small signed pass they show on future requests
to prove who they are. Passwords are never stored as plain text;
they are scrambled with a one-way algorithm so that even someone
who steals the database cannot read them.

Think of it as issuing membership cards: you register once, you
get a card, and from then on you flash the card instead of
re-proving your identity every time.


KEY IDEAS IN PLAIN ENGLISH
--------------------------
- Password hashing
  A password is run through "bcrypt", a one-way scrambler. The
  scrambled result is what gets saved. You can check whether a
  typed password matches the saved scramble, but you can never
  turn the scramble back into the original password.

- JWT (JSON Web Token)
  A string the server gives you after a successful signup/login.
  It contains your user id and email plus an expiry time, and it
  is digitally signed by the server. Anyone can read it, but
  nobody can forge or tamper with it without the server's secret
  key. It expires after a set time (60 minutes by default).

- Secret key from the environment
  The signing key and the token lifetime are read from environment
  variables (JWT_SECRET_KEY, JWT_ALGORITHM, JWT_EXPIRE_MINUTES).
  If they are not set, safe development-only defaults are used, so
  the app still runs on a fresh machine with zero configuration.
  In production you set a real secret and it is never committed.


WHAT WAS ACTUALLY DONE
----------------------
1. Auth helper module was created (app/auth.py).
   - hash_password()        scrambles a new password with bcrypt
   - verify_password()      checks a typed password against the hash
   - create_access_token()  builds and signs a JWT (adds issued-at
                            and expiry timestamps)
   - decode_access_token()  verifies a JWT and returns its contents,
                            or nothing if it is invalid or expired
   Passwords longer than bcrypt's 72-byte limit are trimmed
   consistently so hashing and checking always agree.

2. Request/response shapes were defined (app/schemas.py).
   - SignupRequest   email, password, name
   - LoginRequest    email, password
   - AuthResponse    token, tokenType, userId, email, name
   The email field is checked for a sane basic shape and stored in
   lowercase. The password must be at least 8 characters.

3. Two new endpoints were added (app/main.py):

   POST /signup
     - rejects passwords shorter than 8 characters
     - rejects an email that is already registered
     - hashes the password and saves the new user
     - returns HTTP 201 with a fresh token and the user's details:
         { token, tokenType: "bearer", userId, email, name }

   POST /login
     - looks up the user by email
     - checks the typed password against the stored hash
     - on success returns HTTP 200 with a brand-new token in the
       exact same shape as /signup
     - on any failure (wrong password OR unknown email) returns
       one generic message so attackers cannot tell which emails
       exist

4. Clean error responses were wired up.
   Instead of long technical stack traces, bad input now returns
   tidy JSON:
     - 422  { "detail": "Validation failed",
              "errors": [ { "field": ..., "message": ... } ] }
     - 409  { "detail": "An account with this email already exists" }
     - 401  { "detail": "Invalid email or password" }

For SignUp example 

{
  "email": "test@test.com",
  "password": "test1234",
  "name": "Test User"
}

for login

{
  "email": "test@test.com",
  "password": "test1234"
}

A NOTE ON LIBRARIES
-------------------
The project pins passlib and bcrypt together, but those two exact
versions do not work as a pair (passlib's bcrypt bridge fails to
load). To keep the pinned versions and still ship working hashing,
app/auth.py calls the bcrypt library directly. Behaviour is the
same: bcrypt-hashed passwords, no plain text anywhere.

Email addresses are validated with a small built-in check rather
than the separate "email-validator" package, which is not installed.


HOW WE KNOW IT WORKS
--------------------
The signup and login logic was exercised end to end against a
throwaway in-memory database. All of these behaved correctly:
   - signup succeeds and returns a valid, decodable token
   - signing up again with the same email is rejected (409)
   - a password under 8 characters is rejected (422)
   - a malformed email is rejected (422)
   - login with the right password succeeds and returns a new token
   - login with the wrong password is rejected (401)
   - login with an unknown email is rejected (401, same message)
   - a tampered/garbage token is refused by the decoder
   - very long passwords hash and verify without error


HOW TO TRY IT YOURSELF
----------------------
Start the server, then:

   curl -X POST http://127.0.0.1:8080/signup \
     -H "Content-Type: application/json" \
     -d '{"email":"me@example.com","password":"secret123","name":"Me"}'

   curl -X POST http://127.0.0.1:8080/login \
     -H "Content-Type: application/json" \
     -d '{"email":"me@example.com","password":"secret123"}'

Both return a JSON body containing a "token" you can use later.
The interactive docs at http://127.0.0.1:8080/docs list both
new endpoints.
